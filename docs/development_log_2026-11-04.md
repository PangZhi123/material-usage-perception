# 2026-11-04 联调问题与修改记录

本次处理三个问题：WebSocket 缺少任务结束通知、相机及配置刷新/重启后无法恢复、历史录像包围框间歇显示。前两项已修改并完成自动化验证；第三项仅分析，尚未修复或确认根因。修改位于当前工作区，未进行远端部署。

## 1. 历史分析结束后业务前端没有明确提示（已修改）

现象：同事的业务前端仅依赖 WebSocket，没有收到明确结束消息，容易误以为仍在分析或循环分析。

代码检查：历史视频顺序处理一遍，未发现自动从头重跑逻辑。后台保存结果后更新终态，但内部 `_TASK_STATUS` 被 WebSocket 发送层过滤。原测试页面依靠每两秒 HTTP 轮询获知结束，独立业务前端缺少该兜底。

修改：WebSocket 在待发送的结果消息发送完毕后，发送 `TASK_STATUS`，然后以关闭码 1000 关闭连接。消息字段为 `taskId`、`taskStatus`、`endedAt`、`error`；终态支持 COMPLETED、STOPPED、FAILED。重新连接已结束的任务也发送终态，包括无事件历史的情况。测试页面收到终态后显示提示并停止轮询。

接入要求：业务前端处理 TASK_STATUS，不能将车辆 EVENT_UPDATE 的完成状态当作任务完成，也不能仅凭断线判断分析成功。部署后重启后端。

相关文件：`src/material_usage_perception/api/v1.py`、`api/static/app.js`、`tests/test_api_v1.py`。详细协议见 [WebSocket 任务结束通知](websocket_task_status.md)。

## 2. 相机/配置刷新或重新部署后消失，删除不同步（已修改）

原因：相机登记原来只存于后端内存，重启丢失。标定配置已有文件持久化，但前端列表仅依赖 localStorage，未从服务端恢复；原测试页面没有后端删除入口。仅凭页面缺少记录不能认定标定文件已经丢失。

修改：

- 默认相机注册器将登记信息保存至数据目录 `.private/cameras.json`，启动时恢复；更新与删除同样持久化，写入成功后才更新内存。
- 保存删除标记，避免 YAML 初始登记的相机被删除后重启复活；允许之后重新登记。
- 新增 GET /cameras、DELETE /cameras/{cameraId}、GET /configurations、DELETE /configurations/{configurationId}，统一前缀 `/api/material-perception/v1`。
- 配置删除使用持久化 DELETED 状态，从列表隐藏、详情返回 404、禁止用于新任务；文件及 SQLite 仓库均支持状态更新。
- 测试页面加载时读取服务端相机和配置列表；删除按钮先请求后端，成功后刷新列表。独立业务前端需另行接入。
- 相机列表不返回流地址；数据静态服务禁止访问 `.private`，避免泄漏流地址中的凭据。

删除语义：删除相机登记不级联删除标定配置、视频及历史结果；已启动任务继续使用原连接信息。删除标定配置不影响已启动任务和历史任务配置快照。配置属于逻辑删除，并非物理清除历史文件。

部署要求：新增 `MATERIAL_PERCEPTION_STORAGE_ROOT` 可指定固定持久目录，默认 `outputs/backend_data`。重新部署必须保留或挂载该目录；切换目录前需迁移既有数据。显式注入的自定义相机注册器应实现列表、删除及自身的持久化。

详细说明见 [相机与配置保存、删除](camera_configuration_persistence.md)。

## 3. 15 秒历史视频仅固定约两秒显示包围框（待排查）

用户观察：15 秒测试视频，仅约两秒能看到框，且出现的时间段固定；轨迹始终存在；返回消息一直有 objects，其中也有包围框。暂时无法取得同事业务前端的绘制代码。本次未取得原始报文、录像或前端日志，以上为现场反馈，尚未独立复现。

当前结论：不能简单归因于推送间隔过长。若框消失时仍有有效 bbox，优先检查业务前端的时间筛选、清画布和重绘逻辑。轨迹可以累积保留，而框需要对应播放画面重绘，两者表现不同并不矛盾。尚不能确认具体根因。

已核实的后端行为：

- 历史视频逐帧处理；输出框只含目标类别且具跟踪 ID 的观测，空检测帧允许 objects 为空。
- pushIntervalMs 接口默认 200 毫秒，测试页面默认提交 1000 毫秒；按源视频时间节流，并非墙钟固定推送，也不保证与播放器同步。
- sampleEveryFrames 默认每 10 帧保存一次结果，独立于 WebSocket 节流。采样存档不能作为每帧精确框直接使用。
- WebSocket 节流合并间隔内不同帧的目标及轨迹增量，却使用最后一帧的时间和尺寸；部分框可能不属于消息标记的最后一帧。这是已识别的时间一致性问题，本次未修改，不能据此认定其导致固定两秒显示。

后续排查：

1. 对照消失时的 video.currentTime、实际选中的 frame.capturedAt、task.recordingStartedAt 和 bbox，确认是否选中了正确视频时间的结果。录像内时间应由 capturedAt 减 recordingStartedAt 计算，不能减任务实际执行时间 startedAt。
2. 检查是否对视频时间作严格相等判断、使用消息到达时间匹配、设置过短的清框超时，或每帧清画布但未重绘。
3. 确认前端数据源是 WebSocket 还是采样帧接口，以及结果缓存、最近帧选择和有效期规则。
4. 取得业务前端消息处理/叠框代码及相关报文后复现，再修复。后端跨帧合并语义需单独修改并验证，不能用无限保留旧框掩盖问题。
