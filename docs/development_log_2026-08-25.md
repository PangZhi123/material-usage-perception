# 开发记录（2026-08-25）

## 一、后端算法闭环

### 本次目标

在只有一段离线视频的条件下完成可人工设置、可重复回放的后端算法闭环，不将额外验收数据作为当前阻塞项。

### 已实现

- 正式 YOLO + ByteTrack 离线入口接入 `FrameProcessor`；
- 输出稳定车辆访问、作业事件、物料明细和区域累计结果；
- 增加已有跟踪 JSON 的无界面快速分析入口，调参不需要重跑 YOLO；
- 增加统一 `AlgorithmSettings`，集中校验状态机、ID 拼接和物料参数；
- 最短工作时长 `minimum_dwell_seconds` 可由命令行或后台接口人工设置；
- 增加 FastAPI 健康检查、参数读取/更新和单视频离线分析接口；
- 增加两辆罐车同时进入、同时作业、分别离开和分别计量的测试。

### 不使用 ReID 的多车策略

同一帧的不同 ByteTrack ID 必须占用不同的稳定车辆访问 ID；每辆车拥有独立状态机。
短时 ID 切换只在原轨迹不再出现在同帧、时间间隔和空间距离均满足限制时拼接。
因此正常可见或短时漏检的并行车辆可以区分。长时间完全遮挡、外观相同且交叉换位
时，单靠几何信息无法保证身份正确，输出保留原始轨迹 ID 供人工复核。

### 验证结果

- 使用本机 Python 3.11 运行全部 39 项测试，全部通过；
- 测试覆盖双车同区域同时作业、独立事件和两车分别累计；
- 使用现有 7500 帧视频及 515 条跟踪观测完成 30 秒和 23 秒参数对照；
- 同帧重复抑制后得到 495 条稳定观测和 1 个车辆访问；
- 按当前 `cam2_spatial.example.yaml`，车辆地面点只在第 0～103 帧位于区域内，
  状态机确认的停留时间为 4.16 秒；因此 23 秒和 30 秒均输出 `pass_through`，用量 0；
- 旧开发记录中的 23 秒是车辆从视频开始到离场的时长，不等于当前多边形配置下
  地面点处于计量区域内的时长。后续人工测试应以可视化区域边界和现场业务定义决定
  是否调整多边形，而不是仅为产生计量结果降低时长阈值。

结果文件：`outputs/cam2_acceptance_30s.json` 和
`outputs/cam2_acceptance_23s.json`。

## 二、V1 算法后端接口

### 已完成

- 按 0825 接口规范实现 HTTP 通用响应包络和 MP 错误码；
- 场景图片上传、摘要、尺寸和受控文件访问；
- 特征点、单应矩阵、重投影质量、多边形及不可变配置版本；
- 部署环境变量形式的模型路径、模型版本和置信度配置；
- SQLite 场景、配置、任务、事件和轨迹表；
- VIDEO_FILE 历史任务：已有跟踪结果快速回放或 YOLO+ByteTrack 完整推理；
- 事件分页查询、累计统计和轨迹查询；
- 算法内部字段到 V1 camelCase 字段及枚举的转换；
- 42 项测试通过，包括端到端的合成视频、配置、任务、事件、统计和轨迹测试。

### 当前开发期扩展字段

- `cameraFrameWidth/cameraFrameHeight`：上层相机管理尚未接入，像素标定点计算需要；
- `videoPath/trackingJsonPath`：上层视频文件注册服务尚未接入，本地单视频验收需要。

接入上层系统后，正式请求只需传 `cameraId`、`videoId` 和 `configurationId`，后端从
相机/视频注册信息取得分辨率和受控文件位置。

### 已知限制

- 历史任务当前在请求线程同步执行，适合开发测试，不适合长时间生产任务；
- 停止接口具备幂等数据语义，但同步任务运行中无法从另一个请求即时中断；
- 当前配置执行器使用第一工作区域，多个工作区域的统一车辆身份与跨区域状态仍需扩展；
- WebSocket 实时推送、增量续传和 SNAPSHOT 尚未实现；
- SQLite 适用于当前单机后端，未来多 worker 部署需评估 PostgreSQL 或单独写入服务。

### 当前范围收敛

经确认，当前阶段只开发单工作区域和单监控视频：配置接口强制一个工作区域；任务
接口只接受历史视频；SQLite 通过原子任务认领保证同时只有一个活动任务。并发提交
不会排队，直接返回 `MP0203`。多区域、多视频并行、worker 池和跨摄像头身份问题
统一留到后续阶段。
