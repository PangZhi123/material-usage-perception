# 混凝土物料使用情况智能感知方案

## 1. 建设目标与边界

后端算法负责：检测与跟踪混凝土罐车，根据前端标定信息确定车辆位置，判断车辆是否进入关键施工区域，识别完整作业事件，并根据车辆装载量或容量估算混凝土用量。

前端负责关键点标注和关键区域绘制。后端不提供这些交互，只定义、校验并使用前端传入的数据。

## 2. 现有 ML 原型评估

原工程已有 YOLO 检测、ByteTrack 跟踪试验、单应性坐标转换、关键区域配置和物料统计脚本，可以复用模型权重与部分验证数据。

现有逻辑按照“区域内出现帧数 × 单位时间用量”估算，主要不足如下：

- 普通检测结果没有车辆 ID，无法区分不同车辆；
- 无法可靠处理同一区域内的多辆车；
- 短时漏检可能把同一辆车拆成多个统计片段；
- 区域边界抖动可能反复产生进出记录；
- 车辆停留时间与实际卸料量并非稳定线性关系；
- 矩形区域、硬编码缩放比例和单应矩阵方向不利于工程化；
- 多摄像头可能对同一辆车重复计量。

因此，新工程从“按帧统计”转为“按车辆作业事件统计”。

## 3. 总体算法链路

```text
前端配置（摄像头、关键点、区域、容量）
  -> YOLO 罐车检测
  -> ByteTrack 多目标跟踪
  -> 检测框底边中心（车辆地面点）
  -> 单应性变换到统一施工平面（可选）
  -> 点与多边形的位置关系判断
  -> 车辆进区—停留—离区状态机
  -> 有效作业事件与物料用量估计
  -> 事件明细、累计统计、异常记录
```

## 4. 关键算法设计

### 4.1 检测和跟踪

复用现有 YOLO 权重，将原模型类别 `transporter` 映射为 `concrete_mixer_truck`。使用 ByteTrack 为目标分配 `track_id`。内部唯一键至少包含：

```text
camera_id + processing_session_id + track_id
```

`track_id` 只是单路视频和单次处理会话内的临时身份，不能作为永久车辆编号。

### 4.2 车辆位置

以检测框底边中心近似车辆在地面的接触位置：

```text
ground_x = (x1 + x2) / 2
ground_y = y2
```

若区域画在摄像头画面上，可直接判断；若需统一多摄像头空间，则利用前端标定点计算单应矩阵，将地面点映射到施工平面。配置优先使用 `[0, 1]` 范围的归一化坐标，避免依赖固定分辨率。

### 4.3 区域与状态机

区域采用任意多边形，不限制为矩形。建议状态如下：

```text
OUTSIDE -> ENTERING -> INSIDE/WORKING -> LEAVING -> COMPLETED
```

初始推荐阈值：

- 连续位于区域内 1～2 秒后确认进入；
- 区域内停留不少于 30 秒才判为候选作业；
- 连续位于区域外 3～5 秒后确认离开；
- 漏检不超过 2～3 秒时保持原状态；
- 停留不足阈值时记录为 `pass_through`，不计量；
- 长时间停留但没有确认离场时记录为待确认事件。

所有阈值按秒配置，运行时结合 FPS 换算。可进一步设置外层和核心区域形成滞回边界，降低边缘抖动误判。

### 4.4 用量估计

混凝土量数据源按优先级选择：

1. 运输单实际装载量 `loaded_m3`；
2. 车牌或车辆档案额定容量；
3. 系统默认车辆容量。

默认估算公式：

```text
estimated_usage_m3 = capacity_m3 × load_factor × unload_factor
```

停留时间用于验证是否发生作业，不作为混凝土方量的主要计算依据。每个事件记录 `quantity_source`，明确数据来源。

## 5. 前端输入契约建议

### 摄像头配置

```json
{
  "camera_id": "cam_02",
  "stream_url": "rtsp://example/stream",
  "frame_width": 2560,
  "frame_height": 1440,
  "enabled": true
}
```

### 标定关键点

```json
{
  "camera_id": "cam_02",
  "camera_points": [[320, 260], [2010, 250], [2250, 1240], [210, 1260]],
  "scene_points": [[120, 80], [870, 80], [900, 650], [100, 650]]
}
```

后端校验点数、点序、矩阵可逆性和重投影误差，并保存原始点与计算所得矩阵。

### 施工区域配置

```json
{
  "area_id": "pouring_zone_01",
  "camera_id": "cam_02",
  "coordinate_system": "scene",
  "polygon": [[533, 295], [860, 290], [910, 610], [520, 625]],
  "min_dwell_seconds": 30,
  "enter_confirm_seconds": 2,
  "exit_confirm_seconds": 5,
  "enabled": true
}
```

### 容量配置

```json
{
  "default_capacity_m3": 12.0,
  "default_load_factor": 1.0,
  "default_unload_factor": 0.95
}
```

## 6. 后端输出事件

```json
{
  "event_id": "evt_20260823_cam02_000037",
  "camera_id": "cam_02",
  "area_id": "pouring_zone_01",
  "track_id": 37,
  "vehicle_id": null,
  "vehicle_class": "concrete_mixer_truck",
  "enter_time": "2026-08-23T10:21:18+08:00",
  "exit_time": "2026-08-23T10:32:46+08:00",
  "dwell_seconds": 688,
  "event_type": "unloading",
  "event_status": "completed",
  "capacity_m3": 12.0,
  "estimated_usage_m3": 11.4,
  "quantity_source": "default_capacity",
  "confidence": 0.88,
  "evidence": {
    "enter_frame": 15200,
    "exit_frame": 32400,
    "snapshot_paths": []
  }
}
```

累计统计从事件记录聚合产生，避免累计值与事件不一致。

## 7. 多摄像头策略

MVP 阶段规定一个施工区域只有一个计量摄像头，其他摄像头仅用于观察。第二阶段再结合统一平面坐标、时间窗口、车牌、外观特征和现场拓扑实现跨摄像头去重。

## 8. 开发计划

### 第一阶段：单摄像头离线 MVP

1. 封装 YOLO 检测与 ByteTrack 跟踪；
2. 定义并校验前端配置模型；
3. 实现坐标归一化、单应性转换和多边形判断；
4. 实现车辆事件状态机；
5. 实现按车辆容量的用量估计；
6. 输出事件 JSON、累计统计和证据帧；
7. 使用现有 ML 视频和模型回放验证；
8. 增加几何、状态机和估算逻辑测试。

### 第二阶段：服务化

- 增加 FastAPI 配置与查询接口；
- 增加摄像头 worker 和 RTSP 实时处理；
- 增加事件持久化、任务状态和异常恢复；
- 提供事件列表、累计统计和人工修正接口。

### 第三阶段：准确度增强

- 对接运输单或调度系统；
- 车牌识别和车辆档案匹配；
- 多摄像头车辆去重；
- 更精细的卸料行为识别；
- 基于标注数据校准事件置信度与阈值。

## 9. MVP 验收标准

- 能逐车区分并输出独立事件；
- 同一辆车在区域内连续停留时只计量一次；
- 短时漏检和区域边缘抖动不产生重复事件；
- 经过但未达到停留阈值的车辆不计量；
- 输出事件可追溯到摄像头、帧号、时间和证据图；
- 累计用量等于有效事件估计量之和；
- 所有关键阈值和容量参数均可配置，不硬编码视频分辨率。
